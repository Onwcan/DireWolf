# Security Posture

The public statement of what DireWolf protects, what it does not, and how to report a problem. Detail lives in [THREAT_MODEL.md](THREAT_MODEL.md); mechanism lives in [CAPABILITIES.md](CAPABILITIES.md), [POLICY.md](POLICY.md), [APPROVALS.md](APPROVALS.md), [SANDBOX.md](SANDBOX.md), [NETWORK_SECURITY.md](NETWORK_SECURITY.md) and [SECRETS.md](SECRETS.md).

---

## 1. The claim, precisely

DireWolf claims:

> **The consequences of a compromised model, a compromised agent runtime, or hostile content are bounded by an authorization boundary that the compromised component cannot reach.**

DireWolf does **not** claim:

- that prompt injection can be prevented,
- that a model can be made to reliably refuse manipulation,
- that a sandboxed process cannot be made to do something unhelpful within its granted authority,
- that the system is secure against an attacker who already has root on the host,
- that OCI containers provide VM-grade isolation.

The distinction matters. We are not trying to make the agent behave. We are trying to make its misbehaviour survivable.

## 2. Why the boundary is where it is

Every in-process control — a permission check in the agent's own code, a scanner over its output, an LLM judging whether an action is risky — protects against *mistakes*, not against *adversaries*. If the component being constrained shares an address space with the component doing the constraining, the constraint is advisory.

DireWolf therefore places the authorization boundary at an **OS process and privilege boundary**:

- `dwkd` (the kernel) runs as its own OS user, holds the credentials, owns the policy files, owns the audit log, and performs every side effect.
- `direwolf-runtime` (the agent) runs as a different, lower-privileged user with no credentials, no network route, no filesystem handles and no ability to execute. *(Design: the runtime is M9's, and its network confinement is verified there — [COMPETITIVE_ANALYSIS.md](COMPETITIVE_ANALYSIS.md) §17 G1. What exists now is the authority side of the boundary: `dwkd-authority` identifies its peer through the kernel, M3e.)*
- The only channel between them is a typed socket where every message is canonicalised, policy-checked, capability-verified and audited.

A total compromise of the runtime — arbitrary code execution inside it — yields the attacker exactly the authority that run was already granted, and nothing more.

## 3. Secure by default

Defaults are the security posture. A system whose safe configuration is opt-in will be run unsafely by almost everyone.

| Setting | DireWolf default | Status |
|---|---|---|
| Execution environment | Sandboxed (OCI). Host execution requires config + capability + per-invocation approval. The environment is IMPLEMENTED as a foundation (M5a): an `oci-strict` container prepared, measured from two vantages and reconciled exactly — reachable by no public caller, running nothing but its probe. Sandboxed workloads are M5d's. The host floor is unchanged (M4d): with no approvals before M6, no production build launches a process |
| Network | Denied. Allowlist required. | **M5b (complete, hosted acceptance passed):** a `PROXY_ONLY` environment's only peer is the broker's opaque CONNECT proxy, reaching exactly the run's exact `network.https` hosts through the IP guard, one pinned resolution, server-name agreement and byte budgets ([ADR-0048](adr/0048-m5b-proxy-only-topology-and-connect-proxy.md)); no workload uses it before M5d. **M5c (in progress, pending acceptance):** `net.http`, the kernel's own HTTPS request — every hop decided, resolved only for a granted host, guarded by both daemons, pinned per request ([ADR-0050](adr/0050-m5c-kernel-performed-net-http-ssrf-redirects-and-credential-egress.md)) |
| Filesystem | Workspace only, read and write scoped separately. | IMPLEMENTED (M4a–M4c; Linux) |
| Secrets | Never visible to the agent: an opaque handle, and no API returns a value (M4e). Egress injection's consumer is `net.http`: a credential only at its bound origin, never across one (M5c, in progress). | IMPLEMENTED (M4e); consumer IN PROGRESS (M5c) |
| Approvals | Single-use, expiring, bound to a canonical action. | PLANNED (M6) |
| Durable memory writes | Human-gated when provenance touches untrusted content. | PLANNED (M13) |
| Learned skills | Untrusted until validated and approved. | PLANNED (M11a, M25) |
| Unattended runs | Anything that would require approval is denied instead. | IMPLEMENTED in effect: no approval path exists, so every such decision is a denial; the full semantics are M6's |
| Plugins | Not shipped in V1 (so they cannot be a default risk). | — |
| Audit | Always on. Not optional, not sampled. | IMPLEMENTED for every authority-changing operation (M3d) |

There is no `--yolo`. The nearest equivalent is the `POWER` profile, which is a bounded capability ceiling with a policy rule pack — not a bypass. Every profile still goes through the same single enforcement point.

## 4. Hardening guide

DireWolf's defaults are intended to be the recommended configuration; there is no separate hardening checklist to follow, which is itself a design goal. Beyond the defaults:

1. Run the kernel as a dedicated user; verify with `direwolf doctor` that the runtime user cannot write `kernel.db`, `audit.log` or `policy/`.
2. On Windows, run under WSL2. `doctor` will warn if you do not ([SANDBOX.md](SANDBOX.md) §5).
3. Use `SAFE` for anything that reads content you did not write.
4. Prefer `LOCAL_ONLY` privacy class for sensitive workspaces.
5. Export audit chain heads off-host if you need deletion-detection, not just tamper-detection.
6. Review `direwolf grant list` periodically; a standing grant you forgot is the most likely way you get hurt.
7. Keep `security.allow_host_execution` false unless a specific workflow requires it, and turn it back off afterwards.

## 5. Known limitations

Listed here rather than buried, because a security document that only lists strengths is an advertisement.

1. **Injection within granted authority is not prevented.** If a run may write to your workspace, hostile content can cause a bad write there. Narrow scopes and approvals for irreversible actions are the mitigation; there is no cure.
2. **Containers are not VMs.** A Linux kernel 0-day will escape `oci-strict`. M5a builds and measures the environment (item 19), and runs no workload in it until M5d; today every action still runs on the host (item 17). A stronger `ExecutionEnvironment` is a deferred item, not a shipped one.
3. **Secret redaction is hygiene, not a control.** It cannot catch transformed or encoded values. We rely on secrets not being present, not on scrubbing them.
4. **Host root is game over.** Including deletion of the audit log; hash chaining detects tampering, not deletion, unless chain heads leave the host.
5. **The operator can approve anything.** We show the truth as clearly as we can. We do not override human decisions.
6. **Model providers see prompt content.** Unavoidable for remote inference; `privacy_class` and local models are the answer.
7. **Native Windows host execution has materially lower assurance** than Linux or macOS.
8. **Fail-closed reduces availability.** A kernel fault stops all agent work. This is deliberate.
9. **The TCB is small but not zero.** A compromised kernel dependency is a full compromise.
10. **As of M3d, the authority has durable state; as of M3e it has a process boundary** (see item 11). A DWKP message that decodes is well-formed and nothing more. The capability lattice (M3b) answers "is this within the authority held?", the policy engine (M3c) answers "should this be allowed?", and M3d gives both a durable subject: `kernel.db` holds fenced epochs, leases, admissions, grants and every policy input, and `audit.log` holds a hash chain written before any answer is returned ([ADR-0039](adr/0039-durable-authority-state.md)). There is no approval registry; the canonicaliser (M4a, [ADR-0042](adr/0042-m4a-canonical-filesystem-resolution.md)) resolves what a filesystem path names beneath an operator-bound root, and M4b performs exactly one effect on the result — a bounded `fs.read` through the broker (item 15) — so **no write, no execution, no secret and no sandbox exists** (M4c–M6). Policy inputs whose real producers do not exist yet are derived in the restrictive direction — every run is unattended (`api`), taint starts at none and can only rise — and are not end-to-end proven. And `QueryAuthority` still decides no proposed action: capability text alone cannot say where an action would run or what it would reach, so the proposal is refused (`NO_CANONICAL_ACTION`) rather than decided on invented facts ([ADR-0040](adr/0040-m3d-reconciliation-admission-across-tenures-and-undecidable-proposals.md)); `CanonicalPreview` (M4b) is the typed way to ask what an `fs.read` would be decided.
11. **As of M3e, the runtime cannot lie about who it is** ([ADR-0041](adr/0041-m3e-authenticated-dwkp-transport.md)). `dwkd-authority serve` listens on a Unix-domain socket — nothing else — and, before reading a byte, asks the kernel for the peer's uid (`SO_PEERCRED`) and refuses, unanswered and audited, any uid the operator did not list. The subject is the kernel's; a peer in a pid namespace the authority cannot see, for which the kernel reports pid 0, is judged by its uid like any other and recorded with no pid — read through `nix` since [ADR-0049](adr/0049-peer-credentials-read-soundly-through-nix.md), because `rustix` 1.1.5's read was undefined behaviour for that peer (both daemons' peer checks changed with it); the lease holder is minted once per accepted connection and never shared, so a second connection from the same uid is a different writer; the handshake comes first; the strict decoder refuses every undeclared field, so a runtime cannot assert a policy input; reserved operations have no handler. The socket's directory is the authority's and closed to writers, so the runtime cannot replace the socket to impersonate the authority. A completely compromised runtime can send arbitrary bytes and cannot choose its subject or holder, bypass the handshake or the decoder, use a stale epoch or another connection's holder, reach a reserved operation, or make `QueryAuthority` decide an action — each shown against the real process, and the cross-uid refusal with a real second OS user in CI. **Linux only**: macOS and native Windows have no server rather than a guessed identity. The authority is not memory-safe end to end: SQLite's C runs in its address space.
12. **The Rust and Python protocol readers are separate implementations.** Their agreement is tested with shared vectors, not guaranteed by construction. Neither consults a Unicode database, so the two cannot diverge because their hosts ship different Unicode versions ([ADR-0034](adr/0034-protocol-depends-on-no-unicode-database.md)); any other divergence is a bug a vector has not yet caught.
13. **The authority links SQLite's C.** Since M3d the authority compiles the SQLite 3.53.2 amalgamation — 269,376 lines of C — into its own process, to read and write `kernel.db`. `#![forbid(unsafe_code)]` governs DireWolf's Rust, which contains no `unsafe`; it does not make SQLite memory-safe. The file SQLite parses is authority-owned, in a private directory, opened without URI parsing or symlink following and with `DEFENSIVE` and `trusted_schema = OFF`, which narrows who can hand it hostile bytes; it does not remove the C.
14. **The audit chain is tamper-evident, not tamper-proof.** It detects modification, reordering, interior deletion and — compared with `kernel.db` — removal of acknowledged records. A local attacker who rewrites `audit.log` and every copy of the chain head in `kernel.db` together is not detected; that needs the head anchored off-host, which is operational work that does not exist yet (see §4 item 5).
15. **As of M4b, one effect exists — `fs.read` — and it goes through the broker** ([ADR-0043](adr/0043-m4b-private-broker-channel-and-brokered-fs-read.md)). The authority resolves the path beneath the pinned root, decides with both gates on a complete canonical action built from the resolver's canonical path (`HOST`, the requested byte bound), records a durable intent, and only then opens the checked file for reading and hands `dwkd-broker` that one read-only descriptor over a private Unix-domain socket; the broker reads only from the authority's kernel-reported uid and the authority sends only to the broker's, and each authorisation is single-use because it names the channel the broker issued for that one connection. No MAC key exists anywhere. Stated limits: the **broker must run as its own user** with no write access to workspaces — a descriptor is not a boundary against a holder whose uid could open the file anyway (`/proc/self/fd`), and in the development shared-uid mode the runtime and the authority are indistinguishable to the broker (`REDUCED ASSURANCE`, refused without a flag); a compromised broker can **misreport the bytes it read**, up to the bound, which the authority taints `LOCAL_UNVERIFIED` and cannot verify; an authorisation names an **object, not its content**, so whoever can write that file can change what is read between the check and the read; resolution precedes the gates, so a run can learn whether a workspace path resolves even where it may not read it (never its content); a slow broker holds the authority's single worker for up to 10 seconds per invocation; the **shipped policy packs deny every read** until a home anchor exists (an operator policy is required); and the channel is **Linux only**.
16. **As of M4c, the filesystem tools change files, and the broker's own uid needs write permission to do it** ([ADR-0044](adr/0044-m4c-filesystem-operations-plans-and-atomic-mutation.md)). A call is a plan of canonical actions, every one decided by both gates, and nothing happens unless all allow; an obligation the authority cannot enforce denies. The broker changes one validated name in a directory the authority checked, atomically — a new file synced in a private `0700` staging directory, then an exchange or a no-replace rename, every directory it changed synced before the next step — checking by identity immediately before and after the change that the name binds the authorised object, and undoing a change that reached anything else (or recording `UNKNOWN` when the undo cannot be proved). Stated limits: **a held directory descriptor is not a right to change its names**, so a write-enabled workspace is one the operator grants the broker's uid directory write permission on, and **that grant is ambient** — a compromised broker can change any name in any write-enabled directory while it is compromised; **Linux has no compare-and-swap of a name against an inode**, so the guarantee against a concurrent substitution rests on the operator keeping untrusted writers — the runtime's uid above all — out of the grant (a directory writable by every user is refused), and a trusted writer racing a change can observe it for the moment before it is undone; a replaced file becomes the broker uid's and loses ACLs and extended attributes (its permission bits and group are kept, or nothing changes); an effect whose outcome is not proved is recorded `UNKNOWN` and never repeated by the authority, so a runtime must decide what to do with it — for `fs.move` and `fs.delete`, not to retry blindly; a crash can leave a `.dwkd-<invocation>` staging directory behind — recorded with the invocation's intent, removed by a later sweep only if it provably holds the broker's own uncommitted data, and otherwise retained and identified (the old file, or a removed object, or the evidence of the effect) for the operator — and only beneath the workspace root re-pinned by its fingerprint, never by following the path where the root was; the shipped `balanced` pack performs no write (its write rule requires artifact capture, M8); and it is **Linux only**.
17. **As of M4d, the broker can execute a process — and no production build asks it to** ([ADR-0045](adr/0045-m4d-process-execution-broker.md)). A launch is decided on an **executable identity** — an absolute path with no `PATH` search, resolved to one native file only root or the authority can change, and its SHA-256 — with `argv[0]` its canonical path and every argument passed as exactly its bytes, no shell. The broker re-proves the descriptor the authority opened and executes that descriptor, not a path. But every process M4d could start would run **on the host with the broker's privileges**: no sandbox before M5. So the kernel launches only with the operator's opt-in **and** a per-invocation approval, and approvals are M6's: no flag, feature or variable supplies one, and every production `process.exec` is decided, audited and denied. `workspace_exec_hygiene` and `network_deny` cannot be enforced on the host and deny; a process's descendants can leave its process group; the dynamic loader and shared libraries are not hashed; root and the authority's uid can change an executable between the broker's hash and the exec. Each is stated in ADR-0045 §25.
19. **As of M5a, an execution environment exists — and no public caller can make one** ([ADR-0047](adr/0047-m5a-oci-execution-environment-and-measured-assurance.md)). An `oci-strict` container is prepared through the runtime client the authority resolved and hashed, measured from the runtime's record and by a digest-pinned probe inside it, and used only if every required invariant is observed PASS; the effective level is the lower of declared and measured, with no score. Stated limits: **access to the runtime's socket is root-equivalent**, and separating the broker's uid from the cognition side is the operator's (M5a's evidence runs one uid); the runtime daemon is trusted to report and apply its configuration; `kcmp`, `perf_event_open`, `bpf`, `userfaultfd`, `io_uring_setup`, `add_key` and `request_key` are denied by the profile and **measured from its content only**, not attempted (no safe wrapper exists, and no `unsafe` was added); Docker Desktop stacks a seccomp filter of its own, so "a filter is on" is necessary but not sufficient — the discriminating checks are the host's byte-exact profile comparison and two active canaries; the workspace bind has no `nosuid,nodev` mount flags; a probe the authority pinned is believed. M5a runs nothing inside an environment but the probe, and has no network.

18. **As of M4e, secrets exist — and nothing returns one** ([ADR-0046](adr/0046-m4e-secret-handles-backends-injection-and-redaction.md)). A handle is an identifier; no DWKP operation, CLI command, diagnostic or administrator path returns a value. A value is read from the Linux kernel keyring or an age file only after `secret.use:<handle>` passed both gates and the intent is durable, handed to the broker once as the read end of a pipe, and zeroed in the authority first; `fs.read` content and process output are redacted before the runtime sees them, and the runtime's memory is measured to hold no value. Stated limits: **mode A has no egress consumer and modes B/C no production caller until M5**; **mode C's descriptor is inherited by a grandchild** that does not close it; **`mlock` and `MADV_DONTDUMP` are not implemented**, so a value can reach swap (both daemons do refuse to dump core and are non-dumpable); the value exists in the authority's memory at start (fingerprinting for redaction) and during each use, and in age's and `keyring`'s own buffers, which DireWolf does not zero; a compromised broker sees a value during the invocation it serves; redaction matches exact values and known shapes only — a transformed or split value passes; and the authority's linked dependency closure grew from 27 reviewed crates to 98 on Linux, most of it age's cryptography and localisation stack (ADR-0046 §§25, 27).
20. **As of M5b, an environment can have a network — exactly one peer, the broker's proxy** ([ADR-0048](adr/0048-m5b-proxy-only-topology-and-connect-proxy.md)). A `PROXY_ONLY` environment's namespace has no route; its one peer is a relay forwarding to the broker's CONNECT proxy, which tunnels only to the run's exact `network.https` hosts, resolves each name once on the host and refuses any answer with a blocked address, requires the TLS server name to be the CONNECT host before dialling the pinned address, and enforces byte budgets at the socket. It does not terminate TLS, has no CA and injects no credential: it sees hosts, ports, addresses, server names and byte counts, never paths, headers, bodies or responses. Every direct path a process can try is measured as refused. **Residuals:** domain fronting inside an agreeing tunnel is carried and bounded only by the budget; ECH clients cannot use the proxy; the relay is identified not by a peer credential but by the kernel's uid check on its socket's directory — an ACL that lets only the relay's uid search it, which holds wherever the runtime exposes the directory (Docker Desktop re-exposes every bind source to every WSL distribution; measured) (ADR-0048 §3); the guard judges address ranges, so a granted name that resolves to the host's own public address is reachable on the granted port. No workload uses it before M5d.
21. **As of M5c (in progress, pending owner acceptance and hosted CI), the kernel performs HTTPS requests itself** ([ADR-0050](adr/0050-m5c-kernel-performed-net-http-ssrf-redirects-and-credential-egress.md)). `net.http` is one typed call — a method, a URL, judged headers, a body, at most a credential handle — and nothing the authority decides: no address, resolver, proxy, timeout, trust material or credential value. The authority canonicalises the URL, decides `network.https` (and `secret.use`) through both gates, has the broker resolve only a granted host, judges the whole answer with the same guard the broker used, evaluates policy for every pinned address, charges the run's budgets, records the intent, and only then has the broker — the TLS client, verification always on, Mozilla's roots — send the request to the pinned addresses; a redirect is a new request decided from the start. The authority opens no socket and links no TLS crate (TX047, TX044); the runtime still has no network. **Residuals:** a granted origin is trusted with what is sent to it and may redirect among the run's other grants; an origin that echoes a credential has it taken out by the broker before anything of the response is encoded, but can leave it in the broker's TLS and HTTP libraries' freed memory — never in a message, the audit, the authority or the runtime's answer (ADR-0050 §20, D11, pending the owner's acceptance).

22. **None of this has been tested at scale.** DireWolf has no deployment history. M3 and M4's claims are backed by evidence targets and hosted CI on genuine separate identities; every claim about a later milestone is a design claim until the eval suite and outside review say otherwise.

## 6. Reporting a vulnerability

**Do not open a public issue for a security report.**

Use GitHub private security advisories on the repository (<https://github.com/Onwcan/DireWolf>), as described in [`SECURITY.md`](../SECURITY.md) at the repository root. We will acknowledge within 3 working days and aim to give an assessment within 10.

### In scope

- Any path from model output, tool output, or external content to an unapproved side effect.
- Any capability escalation, including a child exceeding a parent.
- Approval replay, substitution, or binding bypass.
- Secret disclosure to the runtime, to a model, to a log, or to an artifact.
- Sandbox escape; filesystem escape from a workspace; SSRF past the egress guard.
- Audit log tampering that is not detected by the chain.
- Any second enforcement path — i.e. a way to cause a side effect that does not traverse the kernel's decision pipeline. **This is the highest-value class of report**, because the architecture's entire premise is that no such path exists.

### Out of scope

- "I achieved prompt injection" with no chained consequence. Injection is assumed and in-scope only when it produces an unapproved effect.
- Attacks requiring host root or physical access.
- Attacks requiring the operator to approve the malicious action, unless the approval prompt itself misrepresented what would happen — *that* is in scope and is a serious bug.
- Denial of service by exhausting a budget the operator configured.
- Findings against a configuration that disabled a documented default, unless the disabling itself was possible without operator intent.

### Safe harbour

Good-faith research on your own installation is welcome and will not be met with legal action. Do not test against other people's instances.

## 7. Security in the development process

- Every change to `crates/dwkd-authority/`, `crates/dwkd-broker/` or `crates/dwk-proto/` requires review by someone other than the author, and an ADR note if it changes an interface. A change to an authority-facing DWKP operation answers the eight questions in [CONTRIBUTING.md](../CONTRIBUTING.md) "Changing the protocol".
- The security eval suite ([EVALS.md](EVALS.md)) is a merge gate, not a nightly job.
- Every invariant in [README.md](../README.md) has a named test that fails if the invariant is removed.
- `cargo-deny` and `pip-audit` run in CI; new authority-plane dependencies require explicit justification in a new ADR amending [ADR-0019](adr/0019-language-rationale-v2.md), never an edit to it; `dwcheck adr` checks that accepted records are unchanged, anchored to the revision in which each ADR became Accepted rather than to a digest file in the same working tree — see [`adr/README.md`](adr/README.md) rule 1 for why that distinction is the whole point. `cargo-deny` covers advisories, licences, bans, duplicates and sources; `cargo-audit` is deliberately not run as well, because it reads the same RustSec database and a second tool means a second place to suppress a finding ([ADR-0031](adr/0031-repository-layout-and-boundary-enforcement.md)).
- Fuzzing: the protocol parser (`dwk-proto` framing, strict JSON, canonical JSON, envelope/versions) has four libFuzzer targets, and the M3c policy loader has two — one over loading, one over loading and evaluating — because that loader is the first third-party parser inside the authority. All six run weekly and on pull requests that touch them, and a stable-Rust mutation harness runs both sets with every `cargo test`. The path canonicaliser gets targets at M4, when it exists. This is scheduled fuzzing, not continuous fuzzing.
- Generated protocol files (`schemas/`, the Python bindings, the operation inventory) are drift-checked in CI; a hand edit fails the build.
- There is no third-party secret scanner in CI; since M4e an in-repository check refuses committed credential-shaped tokens, the age identity among them. The evaluation and its M4e review are in [CONTRIBUTING.md](../CONTRIBUTING.md) "Secrets". GitHub push protection is a repository setting this repository cannot demonstrate is enabled.
- We publish eval results, including failures. A security posture nobody can check is a marketing claim.
- **Licence checks are not attribution.** `cargo-deny` restricts dependency licences to an allowlist; it does not produce the notices those licences require. The project distributes source only. Before its first binary release, M18 adds per-platform archives with generated third-party notices, an SBOM, a build-provenance attestation, signatures and a reproducibility check ([NOTICE](../NOTICE); [COMPETITIVE_ANALYSIS.md](COMPETITIVE_ANALYSIS.md) §17 G3).
